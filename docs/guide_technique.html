1. Vue d'ensemble et objectifs

Le projet est une boîte noire embarquée sur un voilier. Elle se connecte au réseau d'instruments existants (girouette-anémomètre, loch, GPS…) sans rien modifier au câblage — elle "écoute" juste les données.

Trois objectifs progressifs :

JalonFonctionnalitéMatériel requis
1 — LogRécupérer toutes les données instruments + IMU + baro, les enregistrer en CSV, afficher une interface web sur tablettePi + MiniPlex
2 — CoachEntraîner un modèle XGBoost sur les CSV collectés, afficher le rendement polaire en temps réel (es-tu au bon angle ?)+ BNO055 + BMP280
3 — AutoEnvoyer des commandes MWV au pilote automatique TP22 pour qu'il suive l'angle VMG optimal+ câble NMEA TP22

Le principe fondamental

Le Pi ne touche à rien dans les instruments du bord. Il lit les données via Signal K (un serveur open-source déjà installé sur le réseau), les traite, et écrit seulement sur Out1 du MiniPlex (en mode Override, qui a la priorité sur tout). Si le Pi s'éteint, le MiniPlex rebascule automatiquement vers les instruments bruts après 10 secondes.

3. Hardware — chaque composant expliqué

Le Raspberry Pi 5 est un mini-ordinateur de la taille d'une carte de crédit. Il tourne sous Linux (Debian Bookworm via OpenPlotter). C'est lui qui fait tourner tout le code Python.

3.2 MiniPlex-3USB

Le MiniPlex-3USB est un multiplexeur NMEA 0183. Son rôle : recevoir les phrases NMEA de tous les instruments du bord (4 entrées) et les fusionner en un seul flux USB vers le Pi.

Points critiques MiniPlex

  • In4 est lié à Out1 speed — Le GX2200 (radio VHF, 38400 bauds) doit être sur In1, JAMAIS sur In4, sinon la vitesse de Out1 serait figée à 38400.
  • Out1 en mode Override — Quand le Pi envoie des MWV, il a priorité totale sur Out1. Si le Pi s'arrête → rebascule automatique en 10s.
  • Un seul émetteur vers TP22 — Le mode Override gère ça, ne pas configurer d'autres routes vers Out1.

Vu depuis le Pi, le MiniPlex apparaît comme /dev/ttyACM0 (interface USB CDC — "Communication Device Class"). C'est Signal K qui lit ce port, pas notre code directement.

3.3 IMU BNO055 I2C 0x28

Le BNO055 est une centrale inertielle 9 axes (accéléromètre + gyroscope + magnétomètre). Il contient un processeur intégré qui fusionne ces 3 capteurs pour donner directement des angles d'Euler (roulis, tangage, cap) sans calcul de notre côté.

Branchement GPIO Pi 5

Pin BNO055Pin Pi 5Numéro physiqueRôle
VCC3.3VPin 1Alimentation 3.3V
GNDGNDPin 6Masse commune
SDAGPIO2Pin 3Données I2C
SCLGPIO3Pin 5Horloge I2C

Orientation physique : axe X pointant vers l'étrave, Y vers bâbord, Z vers le ciel.

On lit les registres Euler à l'adresse 0x1A–0x1F. Chaque angle est codé sur 2 octets (little-endian, signé) avec une résolution de 1/16°.

3.4 Baromètre BMP280 I2C 0x76

Le BMP280 mesure la pression atmosphérique et la température. Branché sur les mêmes broches I2C que le BNO055 (c'est le principe du bus : plusieurs capteurs sur 2 fils, chacun avec une adresse différente).

La pression brute du capteur nécessite une compensation mathématique (formule du datasheet BMP280) qui utilise des coefficients de calibration stockés dans la mémoire du capteur lui-même. Sans cette compensation, la valeur lue n'a aucun sens.

3.5 GPS Neo-M9N USB backup

GPS de secours sur /dev/ttyUSB1. N'est utilisé que si Signal K ne fournit pas de position GPS (instruments HS, ou en zone sans couverture). Envoie des phrases NMEA standard $GPRMC / $GNRMC.

3.6 Simrad TP22

Pilote automatique fonctionnant en mode Conservateur d'Allure : il reçoit une phrase MWV (angle de vent apparent cible) et gouverne pour maintenir ce cap. Le câblage pour le Jalon 3 est simple :

4. Protocoles de communication

4.1 NMEA 0183

NMEA 0183 est le standard de communication des instruments marins depuis les années 80. C'est du texte ASCII sur une liaison série (typiquement 4800 ou 38400 bauds). Chaque "phrase" commence par $ et se termine par un checksum.

$WIMWV,045.0,R,12.5,N,A*1B<CR><LF>
 │      │    │  │   │ │  └─ checksum XOR de tout ce qui est entre $ et *
 │      │    │  │   │ └──── A = données valides (V = invalides)
 │      │    │  │   └────── unité N = nœuds
 │      │    │  └────────── vitesse vent apparent : 12.5
 │      │    └───────────── R = relatif (par rapport à la proue)
 │      └────────────────── angle vent apparent : 045.0°
 └───────────────────────── WIMWV = Wind speed and angle, Measured, relative Wind Velocity

Exemples de phrases utilisées dans le projet :

PhraseContenuSource
$WIMWVVent apparent (angle + vitesse)Girouette-anémomètre → MiniPlex → Signal K
$IIMWVVent apparent (même chose, préfixe différent)Idem
$IIVHWVitesse sur l'eau (loch)Loch → MiniPlex → Signal K
$GPRMCPosition GPS + vitesse sol + capGPS → Signal K ou GPS backup
$AIVDMAIS — position des autres naviresVHF GX2200 → MiniPlex → Signal K
$WIMWVCommande angle vent → TP22Notre code → MiniPlex Out1 Override

4.2 Signal K

Signal K est un serveur open-source qui tourne sur le Pi. Il lit le MiniPlex (toutes les phrases NMEA), les parse, et expose les données dans un format JSON unifié via WebSocket. Plus besoin de parser soi-même chaque phrase NMEA — Signal K s'en charge.

Signal K organise les données dans une hiérarchie de "paths" :

{
  "environment.wind.angleApparent": 0.785,  <!-- radians ! -->
  "environment.wind.speedApparent": 6.43,   <!-- m/s ! -->
  "navigation.speedThroughWater":   3.09,   <!-- m/s ! -->
  "navigation.position": {
    "latitude": 47.3,
    "longitude": -2.1
  }
}

Signal K utilise des unités SI, pas marines

Tous les angles sont en radians (pas degrés), toutes les vitesses en m/s (pas nœuds). Notre code convertit systématiquement : ×(180/π) pour les angles, ×1.94384 pour les vitesses.

On s'abonne aux données via WebSocket avec un message JSON :

{
  "context": "vessels.self",
  "subscribe": [
    {"path": "environment.wind.angleApparent", "period": 1000},
    ...
  ]
}

4.3 I2C — le bus pour les capteurs

I2C (Inter-Integrated Circuit) est un protocole de communication sur 2 fils : SDA (données) et SCL (horloge). Plusieurs capteurs partagent les mêmes 2 fils — chacun est distingué par son adresse 7 bits unique.

Pi GPIO Sur le même bus Pin 3 (SDA) ────────────┬──────────────────────────┐ Pin 5 (SCL) ────────────┼──────────────────────────┼─── │ │ ┌──────┴──────┐ ┌────────┴────┐ │ BNO055 │ │ BMP280 │ │ adresse 0x28│ │ adresse 0x76│ └─────────────┘ └─────────────┘ IMU 9 axes Baromètre

Pour lire un registre I2C : le Pi envoie l'adresse du capteur + le numéro du registre, le capteur répond avec la valeur. smbus2 est la librairie Python qui fait ça.

4.4 WebSocket — notre interface web

Le WebSocket est une connexion bidirectionnelle persistante entre le navigateur et notre serveur Python. Contrairement à HTTP classique (requête → réponse), le WebSocket permet au serveur d'envoyer des données à tout moment, sans que le client les demande. C'est parfait pour de la télémétrie temps réel.

Navigateur tablette Pi (main.py) │ │ │──── connexion WS :8081 ─────────→│ │ │ │←─── JSON toutes les secondes ────│ {"awa": 45.2, "aws": 12.1, ...} │←─── JSON toutes les secondes ────│ │ │ │──── {"type":"recording","value":"start"} ──→│ commande UI → Pi

6. src/signalk_client.py — lire les instruments

Ce fichier crée une connexion WebSocket permanente vers Signal K et maintient à jour un objet InstrumentData avec les dernières valeurs des instruments. Il tourne dans un thread séparé pour ne pas bloquer la boucle principale.

Pourquoi un thread séparé ?

La boucle principale doit tourner à 10 Hz (une itération toutes les 100ms). Attendre une réponse WebSocket bloquerait cette boucle. La solution : le thread SignalK tourne en parallèle et met à jour les données. La boucle principale lit ces données sans attendre. On protège les accès concurrents avec un threading.Lock().

src/signalk_client.py — structure de données 
@dataclass
class InstrumentData:
    awa_deg: Optional[float] = None   # Angle vent apparent
    aws_kts: Optional[float] = None   # Vitesse vent apparent
    twa_deg: Optional[float] = None   # Angle vent réel (calculé par Signal K)
    tws_kts: Optional[float] = None   # Vitesse vent réel
    stw_kts: Optional[float] = None   # Speed Through Water (loch)
    sog_kts: Optional[float] = None   # Speed Over Ground (GPS)
    cog_deg: Optional[float] = None   # Course Over Ground
    heel_deg: Optional[float] = None  # Gîte (depuis capteur attitude si dispo)
    lat: Optional[float] = None
    lon: Optional[float] = None
    updated_at: float = 0.0           # timestamp du dernier update

    def is_fresh(self, max_age_s=10.0) -> bool:
        # Données "fraîches" = reçues il y a moins de 10 secondes
        # Si is_fresh() est False : les instruments ne répondent plus → alerte
        return (time.monotonic() - self.updated_at) < max_age_s

async def _listen(self):
    url = f"ws://localhost:3000/signalk/v1/stream?subscribe=none"
    while True:  # boucle infinie = reconnexion automatique si Signal K redémarre
        try:

AIS — traçage des autres navires

Le même WebSocket Signal K reçoit les positions AIS (Automatic Identification System) des autres navires. Le code maintient un dictionnaire _ais avec les positions, SOG, COG, nom et type de chaque navire identifié par son MMSI. Les cibles non vues depuis 5 minutes sont supprimées automatiquement.

7. src/imu.py — la centrale inertielle BNO055

Sur le Pi, on lit les angles d'Euler directement depuis les registres du BNO055. Sur Mac, un stub simule un roulis sinusoïdal (houle). Si le BNO055 est absent (capteur pas encore branché), le code bascule automatiquement sur le stub au lieu de planter.

src/imu.py — lecture des registres Euler BNO055 
def _init_bno055(self):
    # Registre 0x3D = OPR_MODE (Operating Mode)
    # Valeur 0x0C = Mode NDOF (Nine Degrees Of Freedom)
    # Le BNO055 fusionne lui-même accel + gyro + magneto → angles directs
    self.bus.write_byte_data(self.addr, 0x3D, 0x0C)

def read(self) -> dict:
    # Registres 0x1A à 0x1F = Euler Angles (Heading, Roll, Pitch)
    # 6 octets, 2 par angle, little-endian (octet faible en premier)
    # Résolution : 1/16° par unité (donc diviser par 16.0)
    data = self.bus.read_i2c_block_data(self.addr, 0x1A, 6)

    def to_signed(high, low):
        val = (high << 8) | low       # assembler les 2 octets
        return val - 65536 if val > 32767 else val  # convertir en signé

    yaw   = to_signed(data[1], data[0]) / 16.0
    roll  = to_signed(data[3], data[2]) / 16.0
    pitch = to_signed(data[5], data[4]) / 16.0
    return {"roll": roll, "pitch": pitch, "yaw": yaw}

Pourquoi le roulis pour corriger le vent ?

Quand le voilier gîte, la girouette (en haut du mât) se déplace latéralement. Ça crée une erreur sur l'angle de vent apparent : le vent semble venir d'un angle légèrement différent. La correction Kalman (voir section 8) compense cet effet : Δ_AWA ≈ roll × sin(AWA) × 0.5

8. src/kalman_wind.py — filtrage du vent

Le filtre de Kalman est un algorithme mathématique qui combine une mesure bruitée (la girouette, qui oscille) avec un modèle prédictif (l'angle ne change pas brusquement) pour produire une estimation optimale.

Intuition en langage simple

Imagine que tu veux savoir la température exacte dans une pièce. Tu as un thermomètre qui fluctue légèrement (bruit de mesure) et tu sais que la température ne peut pas changer de 10° en 1 seconde (modèle physique). Le filtre de Kalman pondère intelligemment : si la mesure change beaucoup, c'est probablement du bruit → on fait moins confiance. Si elle change peu, c'est probablement réel → on met à jour.

src/kalman_wind.py — paramètres du filtre 
def __init__(self, process_var=0.5, measure_var=8.0):
    kf = KalmanFilter(dim_x=1, dim_z=1)  # 1 variable d'état (AWA), 1 mesure

    kf.x = np.array([[0.0]])   # état initial : AWA = 0°
    kf.F = np.array([[1.0]])   # modèle de transition : AWA_suivant = AWA_actuel (constant)
    kf.H = np.array([[1.0]])   # modèle de mesure : on mesure directement l'état
    kf.P = np.array([[50.0]])  # incertitude initiale : 50° (on ne sait pas)
    kf.Q = np.array([[0.5]])   # bruit de processus : l'AWA peut changer de 0.5°/tick
    kf.R = np.array([[8.0]])   # bruit de mesure : la girouette a ±8° d'erreur typique
src/kalman_wind.py — mise à jour avec correction roulis 
def update(self, awa_raw: float, roll_deg: float) -> float:
    # Correction de l'effet de gîte sur la girouette
    # Quand le voilier gîte de 10° et que le vent est à 45°,
    # la girouette semble déplacée de ~10 × sin(45°) × 0.5 ≈ 3.5°
    roll_correction = roll_deg * math.sin(math.radians(abs(awa_raw))) * 0.5
    z = np.array([[awa_raw - roll_correction]])  # mesure corrigée

    self._kf.predict()   # étape prédiction : avancer le modèle d'un tick
    self._kf.update(z)   # étape correction : fusionner avec la mesure
    return float(self._kf.x[0, 0])

def predict_only(self) -> float:
    # Appelé quand l'IMU "tick" à 10Hz mais que le vent n'a pas changé
    # On fait avancer le filtre sans nouvelle mesure → lissage entre mesures
    self._kf.predict()
    return float(self._kf.x[0, 0])

src/barometer.py — formule de compensation (datasheet BMP280) 
def _compensate(raw_t, raw_p, T1, T2, T3, P1...P9):
    # Phase 1 : calcul température
    # t_fine est une variable intermédiaire utilisée aussi pour la pression
    var1 = raw_t / 16384.0 - T1 / 1024.0
    var2 = (raw_t / 131072.0 - T1 / 8192.0) ** 2
    t_fine = var1 * T2 + var2 * T3
    temp = round(t_fine / 5120.0, 1)

    # Phase 2 : calcul pression (utilise t_fine de la température)
    # Formule polynomiale complexe — directement tirée du datasheet BMP280
    var1 = t_fine / 2.0 - 64000.0
    # ... 8 lignes de calcul → pression en Pascal → convertir en hPa ÷100
    press = press + (var1 + var2 + P7) / 16.0
    return temp, round(press / 100.0, 1)  # hPa

Alerte dépression

Dans main.py, on garde un historique de pression des 3 dernières heures (1 sample/minute). Si la pression chute de plus de 3 hPa en 3h, c'est le signe d'une dépression qui approche rapidement → alerte dans l'UI.

10. src/gps.py — GPS de secours

Si Signal K ne fournit pas de position (instruments HS), un module GPS USB de secours prend le relais. Il tourne dans un thread daemon (le thread s'arrête quand le programme principal s'arrête).

src/gps.py — parsing de la phrase $GPRMC 
def _parse_rmc(self, sentence: str):
    # $GPRMC,123519,A,4807.038,N,01131.000,E,022.4,084.4,230394,003.1,W*6A
    #               │  │           │           │      │
    #               │  position    longitude    SOG   COG
    #               A = données valides, V = invalides
    parts = sentence.split(",")
    if parts[2] != "A":  # A = Active = fix GPS valide
        return

    # Latitude : format DDMM.MMMM → convertir en degrés décimaux
    # Ex: 4807.038 = 48° 07.038' = 48 + 7.038/60 = 48.1173°
    lat_r = float(parts[3])
    lat = int(lat_r / 100) + (lat_r % 100) / 60
    if parts[4] == "S":
        lat = -lat  # hémisphère sud = latitude négative

11. src/nmea_utils.py — construire des phrases NMEA

Pour envoyer des commandes au TP22, on doit fabriquer des phrases NMEA valides. Le checksum est un XOR (OU exclusif bit à bit) de tous les octets entre $ et *.

src/nmea_utils.py 
import functools

def checksum(sentence: str) -> str:
    # XOR de tous les codes ASCII des caractères
    # functools.reduce applique XOR successivement sur tous les éléments
    # format(..., "02X") → hex sur 2 caractères en majuscules (ex: "1B")
    return format(functools.reduce(lambda a, b: a ^ b,
                                  (ord(c) for c in sentence)), "02X")

def build_mwv(awa_deg: float, aws_kts: float) -> str:
    # WIMWV = Wind speed and angle, Measured relative Wind Velocity
    # R = Relative (par rapport à la proue), N = Nœuds, A = valide
    # Exemple de sortie : "$WIMWV,045.0,R,12.5,N,A*1B\r\n"
    awa_deg = round(awa_deg % 360, 1)   # toujours positif, 1 décimale
    aws_kts = round(max(0.0, aws_kts), 1) # pas de vitesse négative
    body = f"WIMWV,{awa_deg:.1f},R,{aws_kts:.1f},N,A"
    return f"${body}*{checksum(body)}\r\n"

Pourquoi flush() à chaque ligne ?

Si le Pi se coupe brusquement (prise de courant à bord…), les données en mémoire tampon seraient perdues. flush() force l'écriture immédiate sur la carte SD. C'est une précaution marine.

13. src/polar_model.py — machine learning polaires

Les "polaires" d'un voilier sont des courbes qui décrivent la vitesse maximale atteignable selon le vent (TWS et TWA). Elles sont habituellement fournies par le chantier sur papier, mais elles ne tiennent pas compte des conditions réelles : gréement vieilli, réglages, équipage, etc.

On entraîne un modèle XGBoost sur les données réelles collectées avec le DataLogger pour obtenir des polaires personnalisées au bateau.

XGBoost — comment ça marche

XGBoost (eXtreme Gradient Boosting) est un algorithme d'arbres de décision en cascade. Il apprend en construisant des centaines d'arbres de décision successifs, chacun corrigeant les erreurs du précédent.

Entrée : [TWS=12kt, TWA=45°, Gîte=8°] ↓ Arbre 1 : TWS > 10? → oui → TWA > 40? → oui → STW ≈ 6.2kt Arbre 2 : (corrige l'erreur de l'arbre 1) → +0.1kt Arbre 3 : (corrige encore) → -0.05kt ... Arbre 200 : petite correction finale ↓ Prédiction finale : STW = 6.35kt
src/polar_model.py — entraînement XGBoost 
def train_from_df(self, df, save=True):
    # Filtrer les données invalides
    df = df.dropna(subset=["tws_kts", "twa_deg", "stw_kts"])
    df = df[(df["stw_kts"] > 1.0) & (df["tws_kts"] > 2.0)]  # au mouillage ou trop peu de vent

    if len(df) < 300:  # minimum 300 points pour entraîner
        raise ValueError("Pas assez de données")

    # Features : TWS, TWA, gîte → Target : STW (ce qu'on essaie de prédire)
    X = df[["tws_kts", "twa_deg", "heel_deg"]].abs().values
    y = df["stw_kts"].values

    # 80% pour entraîner, 20% pour évaluer (éviter le surapprentissage)
    X_train, X_test, y_train, y_test = train_test_split(X, y, test_size=0.2)

    self._model = XGBRegressor(
        n_estimators=200,    # 200 arbres
        max_depth=5,         # profondeur max de chaque arbre
        learning_rate=0.05,  # petit pas → meilleure généralisation
        n_jobs=-1            # utiliser tous les cœurs CPU
    )
    self._model.fit(X_train, y_train)

    # RMSE = Root Mean Square Error = erreur moyenne en nœuds
    rmse = (mean_squared_error(y_test, self._model.predict(X_test))) ** 0.5

def predict_optimal_twa(self, tws_kts, heel_deg, upwind=True):
    # VMG = Velocity Made Good = composante vers le vent (ou sous le vent)
    # VMG = STW × cos(TWA) en montée, -STW × cos(TWA) en descente
    # On cherche le TWA qui MAXIMISE le VMG

    if self._model:
        twas = np.arange(25.0, 90.0, 1.0) if upwind else np.arange(90.0, 171.0, 1.0)

        # Prédire STW pour chaque TWA possible (vectorisé = rapide)
        X = np.column_stack([np.full(len(twas), tws_kts), twas, np.full(len(twas), abs(heel_deg))])
        stws = self._model.predict(X)

        # Calculer le VMG pour chaque TWA et trouver le maximum
        vmgs = stws * np.cos(np.radians(twas)) * (1 if upwind else -1)
        return float(twas[np.argmax(vmgs)])   # TWA optimal

    # Fallback : table générique si pas encore de modèle ML
    twa_up, twa_dw = _generic_optimal_twa(tws_kts)
    return twa_up if upwind else twa_dw

MAX_RATE_DEG_PER_S = 5.0   # changement max d'angle par seconde
MIN_SEND_INTERVAL = 0.5    # envoyer max 2 Hz (pas besoin de plus)

def _rate_limit(self, target: float, dt: float) -> float:
    # Empêche les changements brusques qui feraient "partir" le pilote.
    # Si target = 50° et awa_actuel = 40°, on ne va que jusqu'à 40 + 5*dt.
    # À 2 Hz (dt=0.5s) : max 2.5° par envoi.
    if self._current_awa is None:
        return target
    max_delta = MAX_RATE_DEG_PER_S * min(dt, 2.0)  # cap à 2s si longue pause
    diff = max(-max_delta, min(max_delta, target - self._current_awa))
    return self._current_awa + diff

def send_wind(self, awa_target: float, aws_kts: float):
    if self._serial and self._serial.is_open:
        sentence = build_mwv(awa_out, aws_kts)
        self._serial.write(sentence.encode())  # ASCII → bytes → série

Sécurité Override MiniPlex

Si le Pi ne répond plus (crash, coupure courant), le MiniPlex rebascule Out1 vers les instruments bruts après 10 secondes. Le TP22 retrouve ses données normales. On n'a pas besoin de gérer ce failsafe dans le code — le MiniPlex s'en charge.

class UIState:
    def __init__(self):
        self._lock = threading.Lock()  # protège _data contre les accès concurrents
        self._data = {"awa": None, "aws": None, ...}
        self._cmds = []  # file de commandes reçues du navigateur

    def update(self, **kw):
        with self._lock:  # verrou = une seule opération à la fois
            self._data.update(kw)

    def snapshot(self) -> dict:
        with self._lock:
            return dict(self._data)  # copie = libère le verrou immédiatement

    def push_cmd(self, cmd: dict):
        with self._lock:
            self._cmds.append(cmd)  # WS handler (thread B) écrit ici

    def pop_cmds(self) -> list:
        with self._lock:
            cmds, self._cmds = self._cmds, []  # main.py (thread A) lit ici
            return cmds
src/web_ui.py — WebSocket handler 
async def _ws_handler(self, ws):
    # Deux tâches en parallèle par connexion :
    # - _push : envoie l'état toutes les secondes
    # - la boucle async for : reçoit les commandes du navigateur
    push = asyncio.create_task(self._push(ws))
    try:
        async for raw in ws:
            self._state.push_cmd(json.loads(raw))  # ex: {"type":"recording","value":"start"}
    finally:
        push.cancel()  # annuler le push si la connexion se ferme

async def _push(self, ws):
    while True:
        await ws.send(json.dumps(self._state.snapshot()))
        await asyncio.sleep(1.0)  # 1 Hz vers le navigateur

Calcul du CPA (Closest Point of Approach)

Le CPA est la distance minimale à laquelle un navire AIS va passer par rapport à nous. On l'utilise pour trier les cibles par dangerosité dans l'UI radar.

main.py — algorithme CPA 
def _cpa_nm(own_lat, own_lon, own_cog, own_sog, tgt_lat, tgt_lon, tgt_cog, tgt_sog):
    # Convertir positions en milles nautiques (coordonnées planes approximées)
    # rx, ry = vecteur relatif de position (nous → cible)
    rx = (tgt_lon - own_lon) * 60 * math.cos(math.radians(own_lat))
    ry = (tgt_lat - own_lat) * 60

    # Vecteurs vitesse (en nœuds, composantes N/S et E/W)
    own_vx = own_sog * math.sin(math.radians(own_cog))
    own_vy = own_sog * math.cos(math.radians(own_cog))
    tgt_vx = tgt_sog * math.sin(math.radians(tgt_cog))
    tgt_vy = tgt_sog * math.cos(math.radians(tgt_cog))

    # dvx, dvy = vitesse relative (nous nous rapprochons à quelle vitesse ?)
    # tcpa = temps avant le CPA (en heures)
    # Si tcpa < 0 : les navires s'éloignent déjà → CPA = distance actuelle
    dvx, dvy = tgt_vx - own_vx, tgt_vy - own_vy
    dv2 = dvx**2 + dvy**2
    tcpa = -(rx * dvx + ry * dvy) / dv2
    return math.sqrt((rx + dvx*tcpa)**2 + (ry + dvy*tcpa)**2)
